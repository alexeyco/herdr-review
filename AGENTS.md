# AGENTS.md

See README.md for what this plugin does; docs/development.md for the dev workflow. Only agent-relevant gotchas live here.

## Gotchas

- The version appears in `Cargo.toml` and `herdr-plugin.toml`; keep both in sync (release tags verify both, then run the full CI suite via `workflow_call` before artifacts).
- Build the release binary before `herdr plugin link` testing; a linked plugin does not rebuild itself.
- Call back into herdr through `HERDR_BIN_PATH`, never a bare `herdr`.
- `min_herdr_version` is checked against the running herdr binary; an older local herdr refuses to link.
- Tool binaries resolve PATH-only in the pane environment (the herdr daemon env; the pre-rename `REVDIFF_BIN` override is removed and never read). The first executable `<tool>` on `$PATH` is canonicalized to an absolute path before exec; no candidate, or one that cannot be canonicalized, is a loud error with the tool's install hint — never a cwd-relative guess, because the pane cwd may be the plugin directory.
- The binary is tri-mode, dispatched in `main` from the env: `HERDR_PLUGIN_ENTRYPOINT_ID` is checked first — `review` = review pane (runs the tool, collects, delivers), `setup` = the read-only setup-dialog popup; an unset/blank entrypoint plus `HERDR_PLUGIN_ACTION_ID` = action mode (decides the branch, opens a pane, exits). Pane modes win when both variables are set.
- The manifest declares plugin id `alexeyco.review` (display `name = "Review"`; dots are legal in herdr ids — precedent `ray.plugin-manager`), `[[actions]]` id `open` (keybinding target `alexeyco.review.open`), and two `[[panes]]`: `review` (declared `placement = "tab"`) and `setup` (`placement = "popup"`, title "Review tool setup", `width = "60%"`, `height = 15`), all with `command = ["./target/release/herdr-review"]`. Plugin pane commands are argv-exec, not send-text, so there is no shell layer and no echoed command. lumen is the single stdio exception: the pane pipes and captures its stdout in memory (lumen renders its TUI to `/dev/tty` itself) while stderr still inherits the pane tty.
- The action decides between the two branches: it reads `config.toml` once, and a configured tool detected on `PATH` opens the review pane directly (the main path); anything else — unset, blank, invalid (warned by the config layer and treated as unset), or missing from `PATH` — opens the setup popup and never a review pane. The setup open is `plugin pane open --plugin alexeyco.review --entrypoint setup --placement popup --focus` with no `--cwd`/`--env`/`--workspace` (the 0.9.5 daemon rejects targeted popups with `invalid_params`); its success is the herdr exit status alone, reply body ignored. The review-pane open reply is parsed best-effort (exit 0 already means the pane exists; parse failure only warns and skips the log line). `config.toml` `placement = "popup"` is refused for the review pane with a warning and falls back to `tab`. The dialog itself is one universal layout — the config-file path (or the `herdr plugin config-dir alexeyco.review` hint when nothing resolves), the three alphabetical rows with dim inline brew install commands, and the repo URL — with no dialog-side PATH detection or config read; any key closes it, exit 0.
- `config.toml` is flat keys `tool` (`revdiff`|`tuicr`|`lumen`, anything else warns and counts as unset), `placement` (`tab`|`split`|`overlay`|`zoomed`), and `direction` (`right`|`down`|`auto`; only `split` gets a `--direction` flag) at `HERDR_PLUGIN_CONFIG_DIR` or `herdr plugin config-dir alexeyco.review`, read once per action launch after the context parse (herdr-owned defaults: config at `~/.config/herdr/plugins/config/alexeyco.review/`, state under `~/.local/state/herdr/plugins/alexeyco.review/`). Every degradation warns and uses defaults — config problems never fail the launch. There is no persisted tool choice: the config file is the only chooser.
- Runtime commands may start in the plugin directory, so the action exports `HERDR_REVIEWS_DIR=<repo>` into the review-pane open; pane mode prefers it over its own cwd and runs the tool with `.current_dir(dir)`. The tool selection travels as `HERDR_REVIEW_TOOL`. `HERDR_REVIEWS_*` is not a protected `HERDR_*` key.
- Plugin panes auto-close when the pane process exits (`RuntimeExitAction::ClosePane`, no respawn). Success paths still call `plugin pane close` (best-effort, falling back to `tab close`); error and no-agent paths print their message then block on stdin via `hold_pane` before returning, otherwise the message vanishes. Before the close, the two clean endings (delivered, no-annotations) return focus to the caller's tab — a pane process closing its own pane is killed by the daemon at that call, so anything after the close never runs: the action forwards the context `tab_id` as `--env HERDR_REVIEWS_CALLER_TAB` on the review-pane open only (after the caller pane/agent pairs, before `--focus`; the setup popup gets no env), and the pane calls `herdr tab focus` on it best-effort — one warning on failure, silent skip when unset, never on hold/error paths.
- Review output is written under `HERDR_PLUGIN_STATE_DIR/reviews/` as a single `<pid>-<millis>.out` (pid keeps same-millisecond reviews collision-safe); pane start prunes kept `.out` files older than 7 days, best-effort with logged warnings. It is kept when delivery is skipped (no agent caller, or the tool/delivery failed) and removed on delivery or a clean no-annotation exit. There is no `.rc` or `.started` file; the pane reads the child's exit code directly. revdiff writes the file itself; for tuicr and lumen the plugin writes the collected canonical text, and an empty file exists before the spawn so failure paths keep evidence.
- The delivered agent prompt is capped at 64 KiB (UTF-8 boundary) with a `(output truncated; full annotations kept at <path>)` note; unreadable revdiff output warns and counts as no annotations when the child exited 0, but is a hard error with any other exit code (file kept).
- herdr CLI calls (`tab`, `pane`, `agent`, `config-dir`) have no timeout in plugin API v1, so a hung herdr daemon blocks the action.
- Never push directly to `master` and never merge a PR yourself: every change goes through a branch and a PR the maintainer merges.
- The release version is the maintainer's call: never pick, bump, or assume a version, and never create or push a tag on your own — ask which version is being released first.
